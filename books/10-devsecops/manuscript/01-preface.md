# About This Book

This book is the tenth volume of the DevOps Handbook Series, and it is the volume that guards all the others. *Docker for DevOps Engineers* answered how to package an application, *Kubernetes for DevOps Engineers* answered how to run it, *GitHub Actions for DevOps Engineers* answered how to build, test, and ship it, *Ansible for DevOps Engineers* answered how to configure it, *Terraform for DevOps Engineers* answered how to describe the infrastructure underneath it in code, *Prometheus & Grafana for DevOps Engineers* and *Elastic Stack for DevOps Engineers* answered how to measure and search it, and *AWS for DevOps Engineers* and *Azure & GCP for DevOps Engineers* answered where all of it runs. Every one of those books built pipelines, clusters, and infrastructure that work. This book asks the harder question: **do they survive contact with an adversary?** It is written for the engineer who already owns a delivery pipeline and now owns the CVEs, leaked tokens, audit findings, and 2 a.m. incident calls that come with it.

The industry term for this discipline is **DevSecOps**, and the book treats it as an engineering practice rather than a gate or a department. The material is organized in two parts that mirror the life of a change. Part I, Securing the Software Supply Chain, works the pipeline from commit to artifact: the mental model of what you are defending and what shift-left actually buys; secrets - the credentials that leak in every breach - managed from first commit (`gitleaks` and pre-commit hooks) to platform (a hands-on HashiCorp Vault with policies, dynamic database credentials, and GitHub Actions OIDC auth); hardening GitHub Actions itself, where the pipeline lives; scanning source and dependencies with Semgrep and Dependabot before they become incidents; container image security, from the fat `ubuntu:latest` build to a distroless image with zero known criticals and Trivy as the gate; and the modern answer to "can you prove what you deployed" - artifact signing with Cosign, software bills of materials with Syft, and SLSA provenance, wired into the build so every artifact ships with its own cryptographic identity. Part II, Runtime, Infrastructure, and Operations, secures what is actually running: policy as code for Kubernetes with Kyverno and OPA Gatekeeper so a non-compliant workload cannot be admitted at all; runtime security with NetworkPolicy, Pod Security, and Falco; infrastructure-as-code scanning with Trivy and Checkov and least-privilege IAM design; dynamic application security testing with the OWASP ZAP baseline scan in CI; security telemetry built on the observability stack from the two observability volumes; incident response and the blameless postmortem; compliance as code with kube-bench and automated evidence; and a closing pair of chapters - a **red-team capstone** that attacks the secured pipeline from Part I to prove it holds, and a maturity roadmap for carrying security from a personal habit to a team culture. The parts are sequential; Part II assumes Part I, and the capstone assumes both.

The content reflects the tools as of October 2026. Security tooling moves fast, so the book pins the durable artifacts the same way the series always has: **gitleaks v8** for secrets detection, **Semgrep 1.x** with the OSS rules registry for static analysis, **Trivy 0.6x** as the one scanner used everywhere from images to IaC to dependencies, **Cosign v2** on the Sigstore stack for signing and verification, **Syft 1.x** for SBOM generation, **Kyverno 1.1x** as the book's primary admission controller with **OPA Gatekeeper v3** covered in parallel, **OWASP ZAP 2.1x** for dynamic scanning, **Falco** with its current driver for runtime detection, **kube-bench 0.1x** for CIS benchmarks, and **`actions/checkout` v7** carrying the GitHub Actions examples. The GitHub OIDC `sub` claim change that the cloud volumes documented affects security chapters too, so the federation guidance here matches the current claim format. Where a number genuinely moves - CVE counts, severity ratings, scan durations, free-tier limits - the book says what kind of number it is rather than copying a figure that will age, and every CVE mentioned is a real, historical example used with its public identifier, never a live threat model for software you might ship.

Three conventions run through the book. Commands, policies, YAML, and workflow files appear in monospaced blocks, complete enough to paste into a shell with the tool installed and run - and the running example is the same small web platform, **shopnow**, that the series has grown since the Docker book, now hardened piece by piece until the Part II capstone attacks it for real. Technical terms such as admission controller, provenance, attestation, and blast radius are kept in English and capitalized when they name a platform concept. Notes marked **Best practice** condense operational wisdom, while **Watch out** boxes flag the mistakes that cause the most production pain - the `.env` file that was never in `.gitignore`, the `GITHUB_TOKEN` that could write packages, the unauthenticated Vault dev server that survived past the demo, the Kyverno policy that blocked every deploy on a Friday. Because the book targets practitioners, full labs appear in the six chapters where hands-on practice changes the most: running Vault and breaking its policies, catching a planted secret and a vulnerable dependency in a live repository, shrinking a real image until its scan is clean, signing an artifact and verifying the signature in CI, standing up Kyverno and watching a violating deployment get rejected, and the capstone drill that injects five vulnerabilities into the pipeline and walks through catching every one. The appendices compress the rest into a desk reference: a map of the security tool landscape by category, a command cheat sheet for the tools used throughout, starter configurations you can copy into a repository today, and a troubleshooting guide organized by symptom.

Every chapter closes with a *See also* list, every internal reference is a live link, and the Part dividers, table of contents, and headings are navigable in all three editions - in the PDF the contents carry computed page numbers and the heading tree appears in the outline panel. Security is not a chapter at the end of a project; it is a property of every command in every other chapter. This book is here to make that property boring, repeatable, and yours.
