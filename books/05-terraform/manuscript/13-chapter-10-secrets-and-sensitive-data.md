# Chapter 10 - Secrets and Sensitive Data {#ch10}

## 10.1 Start From the Uncomfortable Fact

Terraform state is plaintext. Every attribute of every managed object - database passwords returned by providers, private keys generated in-resource, connection strings, API tokens passed as variables - is stored in the state file and in its backups, unencrypted, by design: state is the record Terraform diffs against, and the record must be complete. The `sensitive = true` flag on variables and outputs changes *display* (plans, apply output, `terraform output` mask the value) and marks values in the JSON plan output for downstream tooling; it does **not** encrypt state, and anyone with read access to the backend has every secret in it. Every secret-handling decision in this chapter follows from that fact: reduce what flows through Terraform, control who can read state, and prefer mechanisms where secrets never persist at all.

## 10.2 The Control Plane: Protecting State Is Protecting Secrets

The first line of defense is therefore not a Terraform feature but backend hygiene ([Chapter 7](#ch7)): remote state in storage with encryption at rest, bucket versioning (which doubles as backup), least-privilege read access, and per-environment separation so prod secrets are not readable by everyone who can run dev. Where the platform supports it, add state encryption at the storage layer (S3 SSE-KMS, Azure CMK) - and treat the CLI-level state encryption that OpenTofu ships as a reason some estates standardize on it, if threat models demand it. Two corollaries worth writing into policy: never commit state to git (the `.gitignore` from [Chapter 2](#ch2) exists for this reason; `$ git log --all --full-history -- '*.tfstate'` audits the past), and treat saved plan files as secret-bearing artifacts with the same lifecycle as state ([Chapter 6](#ch6)).

## 10.3 Keeping Secrets Out of Terraform Entirely

The strongest pattern is architectural: Terraform orchestrates the *infrastructure of secrets* (a KMS key, a Vault server, an AWS Secrets Manager entry) but not their *values*. The value flows from the secret store directly to the consumer - an application reads it at boot with its IAM role; a pipeline reads it as a step - and Terraform never sees the payload:

```hcl
resource "aws_secretsmanager_secret" "db" {
  name = "atlas/prod/db"
}

# Terraform manages the secret's existence and rotation policy;
# the application fetches the value at runtime with its own identity.
```

When a value *must* appear in Terraform-managed configuration (a provider credential, an init script), inject it at runtime - environment variables (`TF_VAR_*`), `-var-file` generated by the pipeline and deleted after use, or a data source reading from the store - and never a literal in code or tfvars. The grep test is the cheap audit: `rg -n "(password|secret|token)\s*=" --type hcl` should surface variable *declarations* and data-source reads, not assignments.

## 10.4 Ephemeral Resources and Write-Only Arguments: Secrets That Are Never Stored

Terraform 1.10 added the first *language-native* answer to the state problem, and it has become the standard pattern. An `ephemeral resource` queries a provider for data that is guaranteed **never to be persisted** to state or plan - a short-lived database credential from Vault or Secrets Manager, an STS token - and lives only for the duration of one operation:

```hcl
ephemeral "aws_secretsmanager_secret_version" "db" {
  secret_id = aws_secretsmanager_secret.db.id
}

resource "aws_db_instance" "main" {
  # ...
  username                    = "atlas"
  password_wo                 = ephemeral.aws_secretsmanager_secret_version.db.secret_string
  password_wo_version         = 3        # bump to rotate
}
```

The companion is the **write-only argument** (`*_wo`): provider attributes that accept a value at apply time and never store it - the password is sent to the API, used, and discarded. Together they close the classic leak: rotation happens by bumping `password_wo_version`, the secret exists in the store, and it appears *nowhere* on disk. Since 1.10-1.11 era, ephemeral values can flow through variables marked `ephemeral = true` and into write-only arguments across the provider ecosystem; check a provider's schema for `*_wo` support before assuming it. OpenTofu reached parity through its 1.11 release's ephemeral values, so the pattern is portable across both distributions.

::: {.note}
**Best practice - audit what already leaked**

Legacy estates have years of secrets in state. The remediation is rotation, not deletion: rotate the credentials that ever passed through state, migrate new usage to ephemeral/write-only patterns, and let the old values die in old state versions. Deleting a state file (or `state rm`) removes the *record*, not the *access*.
:::

## 10.5 Federation: The End of Long-Lived Keys

Provider credentials themselves are the most recurring secret in any estate, and the 2026 answer removes them: **OIDC federation** exchanges a short-lived, signed token from the execution environment (GitHub Actions, GitLab, HCP Terraform) for cloud role credentials - no key stored, rotated, or leakable. The pattern from [Chapter 4](#ch4) lands here as policy: static cloud keys in provider blocks or tfvars are a finding in review; the pipeline assumes a role per environment ([Chapter 9](#ch9)'s per-environment IAM makes the trust explicit), and the same mechanism extends to pulling from private registries and artifact stores. Where federation is genuinely unavailable (on-prem providers, legacy APIs), the least-bad pattern is a secret store read at run time via ephemeral resources - still nothing persisted, still rotation owned by the store.

## 10.6 A Working Order of Preference

The decision ladder, from strongest to weakest: (1) the secret never enters Terraform - app fetches it at runtime with its identity; (2) the secret enters *transiently* - ephemeral resource feeding a write-only argument; (3) the secret is *orchestrated* - Terraform manages the store entry, pipeline injects the value at apply time; (4) the secret is in state - tolerated only for values that are already protected by backend hygiene and rotation, and scheduled for migration upward. Teams that operationalize the ladder convert "secrets in Terraform" from a dread topic into a code-review checkbox - and the audit trail ([Chapter 11](#ch11) makes it policy) that enforces the ladder is itself Terraform-managed infrastructure.
